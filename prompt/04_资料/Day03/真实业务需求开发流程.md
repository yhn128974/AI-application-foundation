# 🚀 大模型业务落地实战：文本分类工业级标准作业流程 (SOP)

很多同学以为做大模型应用就是“写写提示词、调调 API”，但在真实的工业场景中，**模型调用只占 10% 的工作量，剩下的 90% 都是业务对齐和工程化落地**。

本文将以**“金融数据分类”**为例，带大家拆解从接到需求到代码上线的全生命周期标准流程。

---

## 第一步：需求拆解与业务对齐 (Requirement Alignment)

**核心目标：** 不要急于写代码，先搞清楚业务方到底想要什么。技术与业务的认知往往存在偏差，必须通过“对齐”来弥合。

### 1. 审视与完善标签体系

假设业务方给出的初始标签为：`['新闻报道', '公司公告', '财务公告', '分析师报告']`。

> ⚠️ **实战铁律（避坑指南）：** 必须强制增加一个 **“其他”** 或 **“无法分类”** 的兜底标签。真实环境下的数据充满了噪音（如：广告推销、乱码、与金融无关的闲聊），如果不设兜底，模型只能在已知标签中“强行瞎猜”，导致严重的脏数据污染。

### 2. 跨部门“拉齐”会议

- **痛点：** 业务人员懂业务但不懂大模型边界，他们定义的标签可能存在交集（比如“财务公告”可能也属于“公司公告”）。
- **动作：** 组织产品经理、业务实际使用人、前后端开发一起开会。
- **产出：** 明确分类的**互斥性原则**（如果一篇长文同时包含新闻和财务公告，到底按哪个算？），并彻底敲定最终的输入输出字段。

---

## 第二步：数据探勘与样本定义 (Data Profiling)

**核心目标：** 摸底真实数据形态，评估处理难度。“Garbage In, Garbage Out”（垃圾进，垃圾出）在大模型时代依然适用。

### 1. 构建代表性样本集

不要只拿几条完美的数据来测，必须深入业务系统捞取真实数据：

- **时间跨度：** 错开日期，抽取不同月份的数据，避免时间周期导致的分布单一。
- **极端案例（Edge Cases）：** 故意挑选极短文本（只有一句话）、极长文本（几万字财报）、错别字密集的文本。
- **典型样例对照：**
  - *样例 A（特征明显）：* “央行发布公告宣布降低利率...” → **新闻报道**
  - *样例 B（特征重叠）：* “公司资产负债表显示...” → **财务公告**（需明确这类不能被打入“公司公告”）

### 2. 数据清洗预判

在这一步就要观察数据中是否含有大量 HTML 标签、特殊符号或敏感信息（PII），提前规划数据清洗的逻辑。

---

## 第三步：提示词工程与框架设计 (Prompt Engineering)

**核心目标：** 拒绝简单的对话式 Prompt，采用结构化、工程化的模板来约束大模型的输出。

### 1. 策略分级

- **简单任务：** Zero-shot（零样本）或 Few-shot（少样本）直接搞定。
- **复杂任务：** 涉及几十个分类且边界模糊时，引入 **COT（思维链）**，让模型“先分析特征，再给出结论”，准确率会大幅提升。

### 2. 工业级通用架构模板

在真实代码中，我们通常采用 `<XML>` 标签来做物理隔离，防止大模型产生幻觉或被恶意注入：

```xml
# 金融资讯分类判定系统

<system>
## 角色与任务
你是一位资深的金融数据分析专家。请对输入文本进行精准分类，并严格输出结构化 JSON 数据。

## 分类体系 (Taxonomy)
1. [新闻报道]：宏观经济、行业动态、第三方视角的客观报道。
2. [公司公告]：企业官方发布的非财务类重大事项（如：人事变动、并购）。
3. [财务公告]：包含资产负债表、利润表、营收数据的官方披露。
4. [分析师报告]：券商或研报机构给出的主观预测、评级与投资建议。
5. [其他]：不属于以上任何一类，或包含大量无意义字符的文本。

## 决策边界 (Edge Cases)
- 若文本同时包含“公司动态”和“财务数据”，优先划归为 [财务公告]。
- 若通篇是口语化的股民讨论，一律划归为 [其他]。

## 输出规范 (Output Constraints)
请严格遵循以下 JSON 格式，禁止输出任何多余的解释性文字或 Markdown 标记：
{
  "category": "必须是分类体系中的5个标签之一",
  "confidence": "high|medium|low",
  "reasoning": "简要说明判定的核心依据，限50字以内"
}
</system>

<user>
待分类文本：
{{content}}
</user>
```

> 💡 **实战 Tip：** 在调用 API 时，务必将大模型的 Temperature（温度参数）设置为 0 或 0.1，以保证分类结果的确定性和一致性。

---

## 第四步：测试调优与指标评估 (Testing & Tuning)

**核心目标：** 用数据说话，通过 Badcase（错误案例）驱动模型迭代，而不是靠拍脑袋改提示词。

### 1. 建立“黄金测试集” (Golden Dataset)

准备 200-500 条经过人工精标的数据。**这批数据必须严格隔离**，绝对不能出现在 Prompt 的 Few-shot 示例中，专门用于客观评估模型能力。

### 2. Badcase 驱动迭代

跑完测试集后，重点分析打错的样本：

- **如果是模型没理解概念：** 在 Prompt 的“分类体系”中补充定义的细节。
- **如果是容易混淆：** 在 Prompt 的“决策边界”中增加对比规则（如：“A 与 B 的核心区别在于...”）。
- **如果是缺乏参考：** 挑选极具代表性的 Badcase 和正确的解析，放入 Prompt 作为 Few-shot 示例。

### 3. 核心评估指标选择

不同的业务容忍度不同，切忌盲目追求综合准确率，要根据业务痛点看关键指标：

| 业务痛点         | 核心看重指标           | 实战场景举例                                     |
| ---------------- | ---------------------- | ------------------------------------------------ |
| **误报代价极高** | **精确率 (Precision)** | 资讯推荐（推错标签会引起用户反感、投诉）         |
| **漏报代价极高** | **召回率 (Recall)**    | 负面舆情监控、退市风险预警（宁可错杀，不可放过） |
| **整体要求均衡** | **F1 分数 (F1 Score)** | 标准化的后端数据归档、知识库构建                 |

## 第五步：工程化接入与防御机制 (System Integration)

**核心目标：** 将脆弱的模型 API 变成稳定、高可用的企业级服务。

### 1. 性能与并发规划

- **I/O 密集型（调云端 API）：** 瓶颈在网络。需要开启多线程/异步协程（如 Python 的 `asyncio`），并通过连接池提高吞吐量。
- **计算密集型（本地 GPU 部署）：** 瓶颈在算力。使用 vLLM 等推理加速框架，开启多进程并发，并做好请求排队机制。

### 2. 契约与容错防御机制

不要完全信任大模型的输出，必须在工程层面做好兜底：

- **结构化解析：** 拿到返回结果后，使用 Pydantic 或正则表达式强校验 JSON 格式。如果大模型犯抽多加了 `json` 外壳，代码要能自动剥离。
- **重试机制 (Retry)：** 遇到 API 网络抖动或偶尔的输出格式错误，设定自动重试 2-3 次。
- **降级策略：** 如果大模型服务彻底挂掉或者一直返回乱码，系统默认将其打上 `[待人工审核]` 的标签，保证业务主流程不阻塞。

---

## 第六步：敏捷开发与代码落地 (Coding)

**核心目标：** 拒绝重复造轮子，借助现代工具链快速出活。

1. **AI 辅助编码：** 熟练使用 Cursor、Trae、Claude 3.5 Sonnet 等工具。直接向 AI 喂入“接口文档 + Prompt + 业务要求”，让其一键生成带有异常处理和并发控制的 Python 业务脚本。
2. **沉淀标准组件：** 随着业务的增多，把“调用大模型 → 异常重试 → JSON 解析 → 存入数据库”封装成标准的工具类。
3. **低成本切换：** 后续如果有新的分类需求，只需要修改 Prompt 模板和输入输出定义即可快速拉起一个新服务，实现工程层面的高度复用。
