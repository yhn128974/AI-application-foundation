在大语言模型（LLM）的对话接口（如业界通用的 Chat Completions API 标准）中，`system`、`user` 和 `assistant` 是构建多轮对话上下文的三个核心角色（Roles）。它们通过明确分工，共同定义了人机交互的逻辑与结构。

以下是这三者的具体定义与作用：

### 1. System（系统）

- **是什么：** 给大模型设定的“全局指令”或“人设背景”。它通常位于对话历史的最前端，对整个对话过程起统领作用。
- **主要作用：**
  - **设定角色与基调：** 告诉模型“你是谁”。例如，“你是一个资深的儿科医生”或“你是一个幽默的脱口秀演员”。
  - **确立规则与边界：** 限制模型的行为。例如，“只能用中文回答”、“遇到不懂的问题请直接回答‘不知道’，不要编造”。
  - **提供全局上下文：** 注入不随对话改变的背景信息，比如当前的时间、特定的知识库格式要求等。

### 2. User（用户）

- **是什么：** 最终与模型进行交互的“人类使用者”（或代表人类发起请求的应用程序）。
- **主要作用：**
  - **发起具体请求：** 提出问题、下达任务或提供需要处理的数据。例如，“请帮我写一段 Python 代码”或“解释一下什么是量子力学”。
  - **推动对话发展：** 在多轮对话中，通过不断追问或提供新条件，引导模型深入解决特定问题。

### 3. Assistant（助手）

- **是什么：** 大语言模型本身。它是根据 `system` 的设定和 `user` 的输入，自动生成回复的 AI 实体。
- **主要作用：**
  - **响应与执行：** 直接回答 `user` 的问题或完成其交付的任务。
  - **承载对话记忆：** 在 API 的调用中，过去由 `assistant` 生成的内容会被重新提交给模型，作为历史上下文的一部分。这让模型能够“记住”之前自己说过的话，从而保持多轮对话的连贯性。

### 它们是如何协作的？（示例）

在实际的底层技术调用中，这三者通常以消息列表（List of messages）的形式按顺序组合在一起，打包发送给模型。结构如下：

JSON

```
[
  {
    "role": "system",
    "content": "你是一个中英翻译助手。请将用户输入的中文翻译成地道、专业的英文，不需要任何解释。"
  },
  {
    "role": "user",
    "content": "你好，请问最近的地铁站怎么走？"
  },
  {
    "role": "assistant",
    "content": "Hello, could you please tell me how to get to the nearest subway station?"
  },
  {
    "role": "user",
    "content": "如果是去机场呢？"
  }
]
```

在这个协作过程中：**System** 制定了“翻译且不解释”的硬性规则；**User** 提出了连续的翻译需求；**Assistant** 既输出了第一次的翻译结果，也作为历史记录，帮助模型在面对第二次提问（“如果是去机场呢？”）时，能准确理解用户依然需要的是英文翻译，而不是路线规划。
