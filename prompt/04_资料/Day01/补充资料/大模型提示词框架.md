# 🚀 黑马程序员 · 企业级 Prompt Engineering 高阶实战指南

同学们好！在真实的 AIGC 应用开发与大模型落地中，仅仅依靠“自然语言聊天”是绝对无法构建稳定产品的。企业需要的是高准确率、严格输出格式（如 JSON）以及可预期的决策逻辑。

这份指南提炼了当前大厂最核心的 Prompt 编写规范。掌握这套标准架构，大家在未来的实际工作中，只需要根据具体的业务场景稍加定制和加工，就能直接无缝接入企业级开发流水线。

## 一、 业界主流提示词框架对比

在编写复杂 Prompt 时，我们通常会借助成熟的框架来组织逻辑。

| **框架**              | **核心结构**                                    | **最适用场景**     | **局限性**                 |
| --------------------- | ----------------------------------------------- | ------------------ | -------------------------- |
| **CO-STAR**           | 包含 Context (背景) 到 Response (响应) 的六要素 | 通用分类、文本生成 | 应对复杂决策流时略显不足   |
| **CRISPE**            | 强调 Capacity (能力) 与 Role (角色) 设定        | 创意生成与分析混合 | 在严格分类任务中偏重       |
| **RACE**              | Role (角色) · Action (行动) 等四要素            | 快速搭建原型       | 缺少对模型输出格式的强约束 |
| **Structured Output** | System Prompt + JSON Schema + 结构验证          | 生产级自动化流水线 | 需要工程代码的强配合       |
| **Agentic RAG**       | 检索候选库 → 候选过滤 → 精确匹配判定            | 处理超长分类列表   | 整体系统架构较为复杂       |

**企业级打标/分类任务黄金组合推荐：**

**CO-STAR（明确角色） + 决策树（梳理判定逻辑） + JSON Schema（强约束输出）**

## 二、 核心实战：Prompt 标准七层架构

为了保证大模型在复杂任务中的稳定性，建议采用以下“七层架构”来编写 System Prompt。这种方式相当于给大模型编写了一份严谨的“伪代码”：

Plaintext

```
┌─────────────────────────────────────────┐
│  Layer 1 · 角色与任务（Role & Task）      │  定义身份、核心动作与质量标准
├─────────────────────────────────────────┤
│  Layer 2 · 背景知识（Context）            │  提供业务、公司或行业的关键背景
├─────────────────────────────────────────┤
│  Layer 3 · 标签体系（Taxonomy）           │  明确各项定义（定义 + 包含 + 排除）
├─────────────────────────────────────────┤
│  Layer 4 · 决策流程（Decision Tree）      │  提供有序的、按优先级的判定步骤（核心）
├─────────────────────────────────────────┤
│  Layer 5 · 边界规则（Edge Cases）         │  提供易混淆概念的对比表，指明区分标准
├─────────────────────────────────────────┤
│  Layer 6 · 示例（Few-shot）               │  提供典型案例与边界反例
├─────────────────────────────────────────┤
│  Layer 7 · 输出约束（Output Schema）      │  严格规定 JSON 格式及绝对禁止的行为
└─────────────────────────────────────────┘
```

**关键层级编写避坑指南：**

- **Layer 1 (角色与任务)**：不要只给身份，必须给**质量标准**。例如明确要求“准确率优先于速度；当遇到不确定的情况时，标注 confidence: low”。
- **Layer 4 (决策流程)**：必须用**有序的步骤**替代将所有选项平铺。遵循“匹配 → 输出 → 终止”的逻辑。
- **Layer 7 (输出约束)**：生产环境必须要求严格的结构化输出，并在代码层面对接校验，不合格立刻触发自动重试。

## 三、 提示词工程的五大最佳实践

在不断的工程迭代中，以下 5 条铁律能显著提升大模型在业务流中的表现：

- **决策树优于标签平铺**：不要把 10 个分类直接丢给模型选。应该按优先级逐步排除，保证模型在每一步只需要比较 2-4 个候选选项。
- **构建严谨的“四件套”定义**：每个核心业务概念必须包含一句话**定义**、适用场景（**包含**）、不适用场景（**排除**）以及具象化的**示例**。
- **科学配置 Few-shot（少样本提示）**：示例配置需要全面。2-3 个典型正向案例用于基本匹配；1-2 个边界案例处理歧义；1 个反例明确“什么绝对不能做”。
- **长列表处理采用“检索 + 判定”**：当分类选项大于 20 条时，直接输入会导致严重幻觉。先用向量检索选出 Top-3 候选，再让大模型在这 3 个候选中做精确比对，可大幅降低 Token 消耗并提升准确率。
- **绝对禁止使用情感胁迫式越狱（Jailbreak）**：不要使用“打错标签会导致严重后果或面临罚款”等胁迫话术。这会增加模型的幻觉率。应使用专业驱动话术，如“你的输出质量将直接决定下游系统的准确性”。

## 四、 生产级通用 Prompt 模板

大家在进行实际业务开发时，可以直接复制并修改以下骨架结构：

XML

```
# [业务模块名称] 分类判定系统

<system>
## 角色与任务
<role>你是一位资深的 [特定领域] 架构师/分析专家。</role>
<task>对输入内容进行准确判定，并严格按照要求输出结构化数据。</task>

## 背景
<context>[提供必要的业务知识、前置条件或名词解释]</context>

## 标签/分类体系
<taxonomy>
### [类别A]
- 定义：...
- 包含：...
- 排除：...
</taxonomy>

## 决策流程
<decision_tree>
1. [最高优先级检查] → 若满足，则输出对应结果并终止。
2. [次优先级检查] → 若满足，则输出并终止。
3. [兜底策略] → 输出默认结果。
</decision_tree>

## 边界规则
<edge_cases>
| 对比项 | 区分核心标准 |
| A vs B | [写明关键差异点，比如时间维度、程度深浅等] |
</edge_cases>

## 输出格式
<output_schema>
{
  "label": "必须来自规定白名单",
  "confidence": "high|medium|low"
}
</output_schema>

<constraints>
- 严格输出 JSON，禁止包含任何解释性文字、Markdown 标记或代码块外壳。
- 确保字段名与规范完全一致。
</constraints>
</system>

<user>
请处理以下内容：
{{content}}
</user>

## 参考示例
<examples>
输入：「[典型业务文本]」
输出：{"label": "类别A", "confidence": "high"}
</examples>
```

## 五、 企业级 Agent 工作流集成建议

写好 Prompt 只是大模型开发的第一步。在实际企业项目中，我们通常会结合 **Dify** 或 **LangGraph** 等 Agent 框架进行自动化编排：

1. **输入节点 (Start)**：接收前端或上游系统的业务文本，绑定到变量 `{{content}}`。
2. **大模型节点 (LLM Node)**：载入上述的七层架构 System Prompt，配置合适的 Temperature（分类任务建议设为 0-0.1）。
3. **代码节点 (Code Node)**：编写 Python 脚本拦截 LLM 输出，进行 JSON 强解析和字段 Schema 校验。
4. **条件网关 (Conditional Edge)**：
   - 校验通过且 `confidence == "high"`：自动写入数据库或触发下游业务流。
   - 解析失败或 `confidence == "low"`：路由至死信队列或触发人工复核（Human-in-the-loop）。
