# Day06 Coze 项目案例：AI 面试助手完整笔记

## 今日目标

1. 能说清楚 AI 面试助手项目的业务背景、核心痛点和一期 MVP 范围。
2. 能区分单智能体、多智能体、路由智能体和工作智能体。
3. 能理解循环结构适合处理“数量不固定的一组数据”，例如多个项目经历。
4. 能画出 AI 面试助手的整体业务流程：用户提交材料、路由识别需求、业务模块处理、数据和知识库支撑、输出结果。
5. 能说清楚简历评估模块的完整链路：数据准备、内容分块、并行评估、项目循环评估、结果整合。
6. 能理解违禁词数据库、简历模板知识库、当前日期、文档识别插件在项目中的作用。
7. 能理解项目收益和优化方向，不把项目只讲成“拖节点”，而是能讲成“为就业辅导提效的 AI 工具”。

## 一、今天学习的主线

前几天我们已经学过 Coze 的基础能力：智能体、工作流、知识库、数据库、多模态、循环结构等。今天开始进入项目案例：AI 面试助手。

项目课和功能课不一样。功能课重点是“这个节点怎么用”，项目课重点是“这些能力怎么组合起来解决一个真实问题”。

今天的核心不是把 AI 面试助手所有模块都完整做完，而是先把项目整体理解清楚，再重点体验简历修改模块。

可以把今天的学习路线理解成：

1. 为什么要做 AI 面试助手。
2. 这个项目准备解决哪些就业辅导问题。
3. 为什么一期先做简历修改、面试录音分析、面试题生成和批量处理。
4. 为什么当前阶段选 Coze，而不是一开始就用 LangGraph。
5. 简历评估模块如何从一份简历文件，变成一份可读的修改报告。

## 二、项目背景：为什么要做 AI 面试助手

AI 面试助手来源于一个真实的就业辅导痛点。

学生学习完课程后，需要准备简历、面试题、自我介绍和模拟面试。老师也需要批改简历、听面试录音、总结问题、给学生生成练习方向。随着学生数量增加，人工处理会出现明显效率瓶颈。

这个项目主要解决四类问题：

1. 简历修改问题：学生初版简历质量参差不齐，常见问题包括项目名称雷同、技能和项目不匹配、工作经历和项目经历混写、学历信息位置不合适、表达空泛等。
2. 面试录音分析问题：老师听完整段录音成本高，而文字转写后可以更快分析学生的自我介绍、问答表现和薄弱点。
3. 面试题生成问题：面试宝典内容多，学生容易抓不住重点，需要根据简历、岗位和真实面试题生成更个性化的练习题。
4. 批量处理问题：老师面对多份简历和多段录音时，需要批量初筛，把低级错误先筛出来，把人工精力留给更高级的问题。

项目的价值不是“让 AI 代替老师”，而是让 AI 先做可标准化、重复性强、初筛类的工作，老师再集中处理需要经验判断的部分。

## 三、MVP：先做能验证价值的小版本

MVP 是 Minimum Viable Product，意思是最小可行产品。

公司做项目时，不会一开始就把所有想法都做完，因为时间、人力、预算都有限。更常见的做法是先做一个小版本，验证方向是否可行。

本项目的一期范围主要包括：

1. 简历修改模块。
2. 面试录音分析模块。
3. 面试题生成模块。
4. 批处理模块。

其中，Day06 白天重点体验的是简历修改模块，因为它输入清晰、输出明确、业务价值容易感知，也最适合让学生第一次理解项目化工作流。

## 四、单智能体、多智能体和路由思想

### 1. 单智能体的问题

单智能体可以理解成一个“大而全的人”。它既要判断用户意图，又要查资料，又要改简历，又要分析录音，还要生成面试题。

当业务简单时，单智能体可以解决问题。但当业务变复杂时，单智能体会有几个问题：

1. 提示词会越来越长，维护困难。
2. 一个功能修改可能影响其他功能。
3. 所有能力都堆在一起，定位问题困难。
4. 对复杂任务的处理稳定性较差。

### 2. 多智能体的思想

多智能体可以理解成一个团队。

团队里有一个路由智能体，负责判断用户想做什么；还有多个工作智能体，分别负责具体任务。

在 AI 面试助手里，可以有：

1. 简历评估 Agent。
2. 面试录音分析 Agent。
3. 面试题生成 Agent。
4. 批量处理任务。

路由智能体像前台或调度员。它先判断用户需求，再把任务分给合适的业务 Agent。

### 3. Coze 和 LangGraph 的关系

Coze 适合快速验证业务流程，拖拽式搭建，上手快，适合课程阶段体验项目思路。

Dify 或 Coze 本地版更适合数据安全要求更高、需要本地部署的场景。

LangChain / LangGraph 更适合复杂生产级项目，扩展性强，但学习成本和开发成本更高。

本项目当前选择 Coze，是因为目标是快速做出可体验的 MVP。将来如果项目规模变大、业务复杂度增加、需要更强的并发和可控性，可以考虑用 LangGraph 重构。

## 五、AI 面试助手整体业务流程

AI 面试助手的整体流程可以分成五步：

1. 用户提交材料：学生上传简历或录音，老师也可以批量提交多份材料。
2. 面试助手识别需求：判断用户是要做简历评估、录音分析、面试题生成，还是批量处理。
3. 业务 Agent 执行处理：不同模块进入不同的处理流程。
4. 数据和知识库支撑：违禁词库、简历模板库、真实面试题库、面试宝典、联网搜索等为结果提供依据。
5. 输出结果：生成简历评估报告、录音分析报告、专属面试题或批量处理报告。

注意：项目中的数据和知识库非常关键。没有数据支撑，智能体只能泛泛而谈；有了规则库、知识库和数据库，智能体才能更像一个业务系统。

## 六、AI 面试助手架构图怎么理解

架构图不要照着名词硬背，建议从下往上看。

可以把 AI 面试助手类比成现代物流供应链：

1. 数据与知识层像底层大仓库。违禁词库、简历模板库、面试题库、学生简历和录音都在这里。
2. AI 能力支撑层像自动化设备中心。OCR 负责识别文档，ASR 负责识别语音，RAG 负责检索资料，Reranker 负责重排，大模型负责理解和生成。
3. 业务应用层像加工流水线。简历评估、录音分析、面试题生成、批量处理都是不同流水线。
4. 用户入口层像门店和下单入口。学生可能从 Coze、豆包、小程序、公众号或内部系统进入。

这套架构不只适用于 AI 面试助手，也适用于很多 AI 项目。

更普遍的 AI 项目可以拆成六层：

1. 用户入口层：网页、App、小程序、API、企业微信等。
2. 业务编排层：工作流、Agent、路由、多智能体、LangGraph 状态图等。
3. 模型与工具层：LLM、OCR、ASR、TTS、搜索、数据库工具等。
4. 检索与记忆层：知识库、向量库、RAG、Reranker、会话记忆等。
5. 业务数据层：数据库、文件、用户数据、日志、权限数据等。
6. 治理与运维层：权限、安全、审计、监控、评测、成本控制、人工兜底等。

课堂项目主要让大家先看懂前五层。真实企业项目还会非常重视第六层，因为系统上线后不仅要能跑，还要安全、稳定、可控。

## 七、简历评估模块总体流程

简历评估模块的输入是一份简历文件，输出是一份 Markdown 格式的简历评估报告。

完整流程如下：

1. 数据准备：准备简历文件、违禁词库、当前日期。
2. 文本处理：通过文档识别或链接读取，把简历文件转成文字。
3. 内容分块：把完整简历拆成个人信息、技能、学历、工作经历、项目经历、个人评价等部分。
4. 多维度评估：分别评估各模块内容。
5. 项目经历深度分析：项目可能有多个，所以要用循环逐个处理。
6. 结果整合：把所有模块的评估结果汇总成完整报告。

这个流程体现了一个重要思想：分治。

不要让一个大模型一次性评估整份简历。更稳的做法是先拆开，再分别评估，最后整合。

## 八、数据准备：为什么要先搭资源

简历评估模块需要先准备两个资源：

1. 违禁词数据库。
2. 简历模板知识库。

### 1. 违禁词数据库

违禁词数据库用于存放不建议直接出现在简历中的词，比如课程项目原名、容易导致雷同的项目名、风险表达等。

使用数据库的原因：

1. 方便增删改查。
2. 不需要每次修改提示词。
3. 可以被多条工作流复用。
4. 后续可以通过 API 接入内部系统。

### 2. 简历模板知识库

简历模板知识库用于做查重和参考。项目经历容易雷同，所以需要把用户简历里的项目内容和模板库做对比。

知识库适合存放文档类资料，比如优秀简历模板、项目描述参考、写法规范。

数据库适合存放结构化数据，比如违禁词列表。

## 九、数据准备节点

简历评估工作流一开始会准备三类信息：

1. 查询违禁词数据：从数据库里取出所有违禁词。
2. 简历文字提取：从用户上传的 PDF、DOC 或图片简历中提取文字。
3. 获取当前日期：用于判断毕业时间、工作年限、项目时间是否合理。

这里要注意，当前日期看起来很小，但在简历评估里很重要。

比如学生 2023 年毕业，当前是 2026 年，那么工作年限一般不能写成 6 年。时间类信息必须结合当前日期判断。

## 十、内容分块：把非结构化简历变成结构化字段

简历本身是一段非结构化文本。大模型虽然能读，但如果整段直接评估，很容易混乱。

内容分块节点要把简历拆成结构化字段：

1. `name`：姓名。
2. `base_info`：个人基本信息。
3. `skill`：个人技能。
4. `education`：教育经历。
5. `work_exp`：工作经历。
6. `project_exp`：项目经历，通常要设置为数组。
7. `self`：个人评价或个人爱好。
8. `context`：简历整体总结，供后续节点参考。

项目经历要设置为数组，因为一份简历可能有多个项目。后面要用循环逐个评估。

内容分块的质量非常重要。如果前面分错了，后面评估就会全错。

## 十一、并行评估：为什么不是一个节点从头评到尾

简历评估可以拆成多个模块：

1. 个人信息评估。
2. 技能评估。
3. 学历评估。
4. 工作经历评估。
5. 项目经历评估。
6. 个人评价评估。

除了项目经历，其他模块可以并行执行。

并行的好处：

1. 节省时间。
2. 每个节点提示词更短、更专注。
3. 每个模块问题更容易定位。
4. 降低长上下文带来的理解衰减。

串行像排队，一个做完再做下一个。

并行像多车道，同时处理多个独立任务。

## 十二、各模块评估重点

### 1. 个人信息评估

重点检查：

1. 求职意向是否明确。
2. 是否出现不建议写的期望薪资。
3. 联系方式是否规范。
4. 工作年限和毕业时间是否合理。
5. 个人信息是否影响筛选。

正确做法：信息简洁、岗位明确、时间合理、无敏感或被动表达。

错误做法：求职意向写多个方向，期望薪资写死，工作年限明显夸大。

### 2. 技能评估

重点检查：

1. 技能是否和项目经历对应。
2. 项目中出现的技术是否在技能中体现。
3. 技能中写“熟练”“掌握”的内容，是否能在项目里找到支撑。
4. 技能顺序是否符合岗位要求。

正确做法：技能点与项目互相支撑。

错误做法：技能堆满但项目完全没体现。

### 3. 学历评估

重点检查：

1. 学历、学校、专业、时间是否完整。
2. 学历位置是否适合。
3. 是否需要避短，把更有优势的项目和工作经历放在前面。

学历不是不能写，而是要放在对自己最有利的位置。

### 4. 工作经历评估

重点检查：

1. 工作经历和项目经历是否混写。
2. 工作职责是否具体。
3. 工作经历和项目内容是否冲突。
4. 时间线是否合理。

正确做法：工作经历写岗位职责、业务范围、参与内容。

错误做法：把项目细节全部塞进工作经历，导致结构混乱。

### 5. 项目经历评估

项目经历是简历中最重要、也最容易出问题的部分。

重点检查：

1. 项目数量是否合理。
2. 项目结构是否完整：背景、技术栈、个人职责、成果。
3. 项目背景是否真实可信。
4. 技术点是否合理。
5. 成果数据是否能解释。
6. 是否出现违禁词。
7. 是否与模板库高度雷同。
8. 是否和上下文内容冲突。

项目经历不仅要“看起来高级”，更要能经得起面试追问。

### 6. 个人评价评估

个人评价是可选内容。如果没有，可以不写。

如果写，就要避免空泛表达，比如“本人认真负责、吃苦耐劳、学习能力强”。这些话不是不能写，而是要有事实支撑。

正确做法：用具体经历证明软素质。

错误做法：堆形容词，没有证据。

## 十三、项目经历为什么要用循环

项目经历和其他模块不同，因为项目数量不固定。

有人写 1 个项目，有人写 3 个项目，有人工作多年可能写 5 个项目。

如果不用循环，就很难逐个稳定评估。

循环的逻辑是：

1. 输入项目数组。
2. 每次取出一个项目。
3. 对这个项目做内容评估。
4. 对这个项目做查重评估。
5. 整合这个项目的评估结果。
6. 所有项目处理完后，输出项目评估列表。

循环适合处理列表数据，也就是“数量不固定、但处理规则相同”的任务。

## 十四、项目重复度评估

项目重复度评估通常包含三个动作：

1. Query 优化：把当前项目内容整理成更适合检索的查询文本。
2. 知识库检索：去简历模板库中找相似项目描述。
3. 重复度评估：把当前项目和检索结果对比，判断哪些部分雷同。

不能直接把整个项目原文拿去检索，因为原文可能又长又乱。先让大模型整理成更清楚的查询内容，检索效果会更好。

重复度评估不是为了让学生“完全不能参考模板”，而是提醒学生不要直接照搬，要把项目改成自己的经历、职责和成果。

## 十五、结果整合

前面每个评估节点都会输出自己的结论，但学生最终需要看的不是一堆散乱结果，而是一份完整报告。

结果整合节点要做的事：

1. 接收个人信息、技能、学历、工作经历、项目经历、个人评价等评估结果。
2. 去掉重复内容。
3. 按清晰结构组织。
4. 不杜撰不存在的问题。
5. 输出一份 Markdown 格式的简历评估报告。

这一步是“最后一公里”。没有结果整合，工作流只能算半成品。

## 十六、项目收益和优化方向

项目收益要围绕业务目标衡量。

AI 面试助手的业务目标是提升就业辅导效率，所以收益可以看：

1. 学生自查简历的效率是否提升。
2. 老师批改简历的时间是否减少。
3. 低级错误是否能提前被筛出。
4. 学生是否能获得更具体的修改建议。

注意：技术指标和业务收益不是一回事。

模型准确率、检索效果、OCR 识别质量属于技术指标；节省老师时间、提高简历初筛效率、提升学生修改质量才是业务收益。

后续可优化方向：

1. 替换效果更好的模型。
2. 替换更强的 OCR 或文档识别能力。
3. 增加学生历史简历查重。
4. 记录调用信息，帮助老师分析学生简历共性问题。
5. 将 Coze 流程迁移到 LangGraph，实现更强可控性。

## 十七、简历评估全节点总览

简历评估模块可以拆成 N0 到 N12，其中 N9 项目经历循环内部又包含 N9a 到 N9e。课堂上不需要死背编号，但要能理解每个节点在链路里的位置。

| 节点 | 名称 | 作用 |
|---|---|---|
| N0 | 开始节点 | 接收用户上传的简历文件 |
| N1 | 简历文字提取 | 把 PDF/DOC 简历提取成文本 |
| N2 | 违禁词查询 | 从数据库取出违禁词列表 |
| N3 | 获取当前日期 | 为工作年限、毕业时间、项目周期判断提供时间基准 |
| N4 | 简历内容分块 | 把简历全文拆成结构化字段 |
| N5 | 个人信息评估 | 检查求职意向、联系方式、薪资、年限等 |
| N6 | 技能评估 | 检查技能和项目是否互相支撑 |
| N7 | 学历信息评估 | 检查学历完整性、位置和学校信息 |
| N8 | 工作经历评估 | 检查工作职责、时间线和项目是否混写 |
| N9 | 项目经历循环 | 遍历项目数组，逐个项目评估 |
| N9a | 项目经历评估 | 检查单个项目的结构、技术、职责、成果、违禁词 |
| N9b | 项目 Query 优化 | 把项目内容整理成更适合检索的查询文本 |
| N9c | 简历模板库检索 | 从知识库召回相似项目模板 |
| N9d | 简历重复度评估 | 判断项目与模板库是否高度雷同 |
| N9e | 单项目结果整合 | 合并单个项目的规则评估和查重结果 |
| N10 | 个人评价评估 | 检查个人评价是否空泛、是否有事实支撑 |
| N11 | 评估结果整合 | 汇总所有模块结果，生成完整报告 |
| N12 | 结束节点 | 输出 Markdown 简历评估报告 |

模型选型也要有依据：

1. 内容分块用大上下文模型，因为简历可能很长。
2. 技能、工作经历、项目评估、结果整合用深度思考模型，因为规则多、推理重。
3. 学历评估可以配合搜索能力，减少学校信息判断中的幻觉。

## 十八、今日易错点

### 易错点 1：把知识库和数据库混用

错误：把违禁词做成知识库，或者把简历模板做成数据库。

正确：违禁词是结构化列表，适合数据库；简历模板是文档内容，适合知识库。

### 易错点 2：把整份简历直接交给一个大模型评估

错误：一个节点从头到尾评估所有内容。

正确：先分块，再分别评估，最后整合。

### 易错点 3：项目经历不用循环

错误：假设每个人只有一个项目，用一个固定节点处理。

正确：项目经历数量不固定，要用循环逐个处理。

### 易错点 4：结果整合节点杜撰问题

错误：整合时为了“看起来完整”生成不存在的问题。

正确：只基于前面评估结果整合，没依据就不要写。

### 易错点 5：只会拖节点，不会解释业务价值

错误：项目讲成“我用了几个节点”。

正确：项目要讲清楚解决了什么痛点、为什么这么设计、产生了什么收益、还有哪些优化方向。
